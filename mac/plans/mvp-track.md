## 1. Why a separate track

§9.3 builds the port in horizontal layers: tests, then the full Core, then the PAL, then the UI. A launchable app appears only after P0, P1, P2 and P5.0, roughly 6–9 weeks in. That is too late to learn whether performance and UX are good enough.

This track cuts one **vertical slice** through the same layers: just enough Core, shims, natives and UI to open a library, browse it and read a book on a real Mac. The riskiest assumptions get tested in about 3–5 weeks, and the owner can judge performance and UX before committing to the full plan.

The slice is not throwaway. It builds the same projects as the full plan (shadow projects, compat shims, CLI harness, Avalonia shell), only with less breadth.

## 2. What the MVP is

A double-clickable, ad-hoc-signed `ComicRack CE (MVP).app` for Apple Silicon that does the following:

1. **Open a library.** Either scan a folder of CBZ/CBR/CB7/CBT (plus PDF if M1.4 lands it), or load a *copy* of a Windows `ComicDb.xml` with a path-prefix remap.
2. **Browse.** A virtualized thumbnail grid with sort (series, title, added) and a text search. A sidebar shows the DB's existing lists and smart lists. These are read-only and evaluated by the Core matchers.
3. **Read.** A reader window with single page and two-page spread; fit width, height and best fit; keyboard and trackpad paging; zoom/pan; native full screen; and the right-to-left flag.
4. **Persist.** The DB and the last page read are saved on quit, into a separate MVP data folder. The app never writes to a Windows DB.

**Not in the MVP** (still in v1 scope): metadata editing and ComicInfo write-back, the smart-list editor, export, the backup UI, preferences, scripts (spiked separately, §7), HEIF/AVIF/JXL, PAL beyond paths and natives, Developer ID signing/notarization, and localization of new UI.

A 24 bpp stride is the row bytes rounded up to a multiple of 4; the order is BGR. - **Image ownership (the rule for M2.2b/M2.3).** `PixelBlock` owns the `SKBitmap` with a reference count. The cache holds one reference, and every `SKImage` handed out is a **new** `SKImage.FromPixels` over the same memory (no copy, tested: same address) whose Skia release callback gives one reference back. So the cache evicting an entry never frees pixels that a cell still draws (tested: evict, draw, then `Clear`, then dispose, with `PixelBlock.LiveCount` checked at each step), a consumer may `Dispose` its own image at any time, and an image nobody disposes is freed by the garbage collector (tested with forced GCs; the release callback runs synchronously on `Dispose` and on the finalizer thread). When the cache lets go of a block that images still use, `GC.AddMemoryPressure(bytes)` is called until it is freed (Skia bitmaps are native memory the GC does not see; the effect on collection timing is **not** tested, only that it is balanced). Memory held by consumers after eviction is not counted in the 256 MB bound; `PixelBlock.LiveCount`/`LiveBytes` (process-wide statics) report all pixels alive, for M2.2b's memory measurement.
- **Decision: the decoder does not wrap the Core's `ThumbnailImage.Bitmap` with `SkiaInterop.GetSKBitmap`.** That bitmap belongs to the `ThumbnailImage`: `GetThumbnail(height)` replaces and disposes it when another height is asked for, `MemoryOptimizedImage` releases it after `SecondsToKeepDecodedImage` (15 s) without a request, and the cache disposes the image on eviction; the Core protects its own users only with `ItemMonitor.Lock(bitmap)` while painting. - **Wide pages are only known after decoding.** The Core fills `ComicPageInfo.ImageWidth/Height` (`UpdatePageSize` from the cache manager, saved in the database) when it first reads a page, and nothing tells the layout. `PageService.Decoded(page, w, h)` (called on the decoding thread before the page can be found in the cache) feeds `PageCatalog.Learn`; the catalog bumps its `Version` when a page's wide/narrow property differs **from what the layout last saw** (`seenWide`, not from what the Core says now: a first version compared with the Core and missed a size the Core had learned a moment before, found by the real-CBZ test). `ReaderViewModel.LoadAsync` loops (4 rounds at most): after the pages arrive it asks the layout again; if the spread changed, the pictures still wanted are kept and the others are requested, so the screen shows the corrected spread once. A jump to a page whose earlier pages were never decoded (Home/End/resume in a new book) uses the "not wide" assumption for them, so the pairing parity there can differ from the true one until those pages are known (the Core remembers sizes, so only the first reading of a book is affected).
- **Fit and zoom.** `ContentPlacement.Place`: scale = fit scale x zoom; the content (one page, or the spread as one image, or a lone page with its blank half) is centred on an axis where it is smaller than the viewport, else scrolled and clamped (an epsilon of 1e-6 avoids a phantom scroll when a size is exactly the viewport's). **Fit Height is now the height of the window** (a wider page or spread pans sideways; the M2.3a "held to the window width" clamp is gone). The Core's `BestFit` ("larger of the two", cropped), `Original` and `FitWidthAdaptive` are still treated as Fit. Zoom is relative to the fit (1 = fit; 1 to 8; x1.25 a step; Cmd+= (`Key.OemPlus`, also with Shift), Cmd+- (`Key.OemMinus`), numpad +/-, Cmd+0 resets zoom and scroll); a zoom about a point keeps the content under the point where it is as far as the edges allow (tested, centre and corners); the zoom survives page turns, the scroll restarts at the top, at the right edge when reading right to left.
- **Input (Avalonia 12.1.4).** `Gestures` is internal in Avalonia 12: the pinch events are `InputElement.PinchEvent` / `PinchEndedEvent` (touch, `PinchGestureRecognizer`; `Scale` is cumulative, the view applies the ratio to the last one) and the macOS trackpad pinch is `InputElement.PointerTouchPadGestureMagnifyEvent` with `PointerDeltaEventArgs.Delta.X` (assumed: the change of magnification, 0.1 = 10 %, applied as `1 + Delta.X`). The headless platform cannot send a magnify; the test builds the event with its public constructor and raises it on the view (the zoom, the focal point and `Handled` are checked), so the handler is tested but **the scale of the real values is not**. Drag: left button down on a pannable page captures the pointer, the content follows it (`SizeAll` cursor), released on button up or capture loss. Wheel: when the content overflows sideways (zoomed, or Fit Height on a spread) the two-finger scroll pans both ways and **does not turn pages** (the swipe recognizer is reset); otherwise a horizontal swipe turns one page as before (reading right to left the other way) and a vertical one scrolls. Arrow keys: Left is next and Right previous when reading right to left; Page Down/Up, Space, Home, End do not change.
- **Menus and keys.** View: the fit modes, Zoom In/Out/Actual Fit (Cmd+= / Cmd+- / Cmd+0), One Page / Two Pages / Two Pages (Adaptive) (Option+Cmd+1/2/3, radio), Read Right to Left (Option+Cmd+R, check), Enter/Exit Full Screen (Ctrl+Cmd+F). Option+Cmd was chosen because Cmd+Shift+3/4 are the macOS screenshot keys. `HandleKey` also handles these chords, so they work if the menu does not take them.
- **Full screen.** `ReaderViewModel.IsFullScreen` and `WindowState` follow each other (the green button or macOS leaving full screen reaches the model); Esc leaves full screen first. On the headless platform setting `WindowState.FullScreen` works and is tested; the real native transition (the Space animation, the menu bar, the window restoring its size) was not seen.
- **Prefetch.** The window is the spread, the next 2 spreads and the previous one: 8 pages for a normal middle spread (single page: 4). The cache never evicts window pages, so a window of 8 pages of 2 to 6 MP holds up to about 190 MB decoded (the 160 MB bound is for pages outside the window). Tested: at position 3 of 20 the pages 1 to 8 are decoded and nothing else, and the next spread is shown without waiting. Not measured: spread page-turn time and memory on Metal (M2.4).

   ```bash
   git diff --name-only master...HEAD | grep -vE '^(mac/|MACOS_NATIVE_PATH\.md$|\.github/workflows/mac-)'
   ```
   It must print nothing.
2. **One task per session, one branch per task.** The branch is `mac/<task-id>` (for example `mac/M0.2`), or `worktree-<task-id>` when run in a worktree, off `mac/mvp`. It merges into `mac/mvp` (§10).

4. **Accept checks are commands.** Run every accept check and paste its output in the PR description. A task is not done until its checks pass.
5. **STOP conditions win.** When a task's STOP condition triggers, commit what works, write what you found under the task, and end the session.
6. **Two failures mean the task is too big.** If a task fails its accept checks after two serious attempts, stop and propose a split into smaller tasks in §9. Do not keep iterating.
7. **Record facts.** Append new facts that later tasks need to §3, in the same PR.
8. **No model identifiers or session links** in code, comments or docs (guardrail 8).

## 10. How to run a task

### 10.1 One-time setup
1. Check that `claude -v` reports 2.1.284 or later. If not, run `claude update`.
2. Create the integration branch and commit this plan on it: `git switch -c mac/mvp master`.
3. Ignore worktrees locally, without editing the repo: `echo ".claude/worktrees/" >> .git/info/exclude`.
4. Optional, for parallel tasks: put `{"worktree": {"baseRef": "head"}}` in `.claude/settings.local.json`. Without it, `claude -w` branches from `master` instead of the `mac/mvp` checkout you launch from.

### 10.2 Model and effort
Pass both as **launch flags**: `--model sonnet --effort <level>`.
- Flags override your settings files for that session only.
- In-session `/model` and `/effort` save to `~/.claude/settings.json` and would change your defaults everywhere.
- Sonnet's default effort is `medium`, so always pass `--effort`.

| Effort | Tasks |
|---|---|
| `low` | M2.6 |
| `medium` | M0.2, M1.4, M1.5b, M1.5c, M1.6, M1.7, M1.8, M2.0b, M2.2c, M2.4, M2.5 |
| `high` | M0.3a, M0.3b, M0.4, M1.1, M1.2a, M1.2c, M1.3, M1.5a, M2.0a, M2.1, M2.2b, M2.3b, S3, S4, P0 tests; **all reviews** |
| `xhigh` | M1.2b, M2.2a, M2.3a, S6 (pixel formats, concurrency and cancellation, the reader core, re-entrant modal loops) |

Do not use `max`. When `xhigh` is not enough, split the task (§4 rule 6) instead.

### 10.3 Run a task (sequential, the normal case)
```bash
git switch mac/mvp && git switch -c mac/M0.2
claude --model sonnet --effort medium "Read mac/plans/mvp-track.md (§3, §4 and task M0.2) and MACOS_NATIVE_PATH.md §0 and §9.2. Execute task M0.2 only, following §4. Run every accept check, update the task's Status line, and commit on the current branch. Do not push. End with a short report: files changed, accept-check output, STOP findings, items added to §9."
```
For another task, change the task ID (in the branch name and in both places in the prompt) and set the effort from §10.2.

### 10.4 Run tasks in parallel
Use this only for tasks joined by `|` in §8. Launch from the `mac/mvp` checkout, with step 4 of §10.1 done:
```bash
claude -w M1.2b --model sonnet --effort xhigh "<same prompt, with M1.2b>"
```
After merging, clean up with `git worktree remove .claude/worktrees/M1.2b`.

### 10.5 Review and merge (every task)
1. Start a fresh session on the task branch with `claude --model sonnet --effort high`, then run `/code-review high`.
2. Run the §4 rule 1 check yourself.
3. Merge: `git switch mac/mvp && git merge --no-ff mac/M0.2`.
4. Push `mac/mvp` when you want CI (after M1.7).
